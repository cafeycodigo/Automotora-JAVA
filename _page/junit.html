¿Por qué existe el método auxiliar private Vehiculo crearFicha()?

En VehiculoDAOTest, para no repetir la construcción del objeto en cada prueba (principio DRY · Don't Repeat Yourself), se extrae un método privado crearFicha() que devuelve una instancia válida de Vehiculo lista para usar.

Anotaciones esenciales del ciclo de vida en JUnit 5

Anotación Cuándo se ejecuta Uso recomendado en tu proyecto Java
@Test Marca un método como caso de prueba ejecutable. Cada regla de negocio de Vehiculo o VehiculoDAO debe tener su propio método @Test.
@BeforeEach Se ejecuta automáticamente antes de cada método @Test. Ideal para inicializar dao = new VehiculoDAO(); sin repetir ese código en cada prueba.
@DisplayName("...") Personaliza el nombre legible del test en el reporte de NetBeans/Maven. Permite describir la regla en español claro en la ventana de resultados de pruebas.
@AfterEach Se ejecuta después de cada método @Test. Útil cuando una prueba abre recursos externos que deben limpiarse al terminar cada caso.
Referencia Rápida JUnit Jupiter

¿Qué aserción elegir en cada caso de prueba?

Todas las aserciones se importan de forma estática desde org.junit.jupiter.api.Assertions.*. Recuerda la regla de oro en assertEquals(esperado, obtenido): el primer argumento siempre es el valor esperado, y el segundo es el resultado devuelto por tu código Java.

Grupo 1 · Valores, Booleanos y Referencias

Comprobación de estado y retorno de métodos

  • assertEquals(esperado, actual) y assertNotEquals(...) comparan igualdad usando .equals() o el valor primitivo.
  • assertTrue(condicion) y assertFalse(condicion) verifican retornos booleanos. El primer dao.guardar(ficha) debe devolver true y el segundo con la misma clave, false.
  • assertNull(objeto) y assertNotNull(objeto) verifican ausencia o presencia de un objeto al llamar a dao.buscar(...).
  • assertSame(esperado, actual) comprueba que ambas variables apunten exactamente a la misma instancia en memoria (==).
Grupo 2 · Excepciones, Agrupación y Colecciones

Validación de errores y pruebas múltiples

  • assertThrows(ClaseExcepcion.class, () -> codigo) verifica que el bloque dentro de la expresión lambda () -> lance la excepción indicada.
  • assertDoesNotThrow(() -> codigo) garantiza que una operación válida se ejecute sin lanzar ninguna excepción.
  • assertAll(() -> ..., () -> ...) ejecuta varias aserciones juntas y reporta todos los fallos a la vez.
  • assertIterableEquals(listaEsperada, listaActual) compara que dos listas devueltas por el DAO contengan los mismos elementos y en el mismo orden.
Cómo funciona la expresión lambda () -> en assertThrows

¿Por qué hay que escribir () -> dentro de assertThrows?

Si llamaras al setter inválido directamente sin el () ->, Java ejecutaría el setter antes de entrar a assertThrows, y la excepción detendría el test sin que JUnit pudiera capturarla. La expresión lambda () -> entrega la instrucción para que JUnit la ejecute dentro de su propio bloque try / catch.

Cómo ejecutar las pruebas y generar el reporte de cobertura JaCoCo en Maven y NetBeans

El archivo pom.xml incluye tres piezas clave para el testing profesional: la dependencia JUnit Jupiter (con <scope>test</scope>), el plugin Maven Surefire y el plugin JaCoCo (que mide qué porcentaje de líneas e if / else fueron ejecutados por tus tests).

Comandos en terminal
# 1. Solo ejecutar los tests unitarios:
mvn -f AutomotoraDAO/pom.xml test

# 2. Limpiar, probar y crear el informe HTML de JaCoCo:
mvn -f AutomotoraDAO/pom.xml clean verify

¿Cómo leer el semáforo de JaCoCo?

Al abrir target/site/jacoco/index.html en tu navegador verás cada línea de Vehiculo y VehiculoDAO coloreada:

  • 🟢 Verde: Línea o rama completamente ejecutada por al menos un @Test.
  • 🟡 Amarillo (rombo): Rama parcialmente cubierta (ej. probaste cuando el if dio true, pero ningún test probó cuando da false).
  • 🔴 Rojo: Código que ningún test ha ejecutado todavía.
